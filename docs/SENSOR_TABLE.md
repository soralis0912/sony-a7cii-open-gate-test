# センサー読み出しモードテーブル（特定済み・2026-11-24）

オープンゲートの第一歩、「センサーの全行を読む」ための対象が**特定できた**。
実機では未検証。

## 置き場所は appFw ではない

A7 IV キットのセンサー系デザイン（`ogsq_v3` / `og57n_v1`）が触っている
アドレス帯（`0xbf7638`〜`0xfb4044`）は 18MB 程度のイメージに収まる。
A7C II の `appFw.so` は 95MB で、そもそも桁が合わない。
`DrvParam` のような手がかり文字列も `appFw.so` には無い。

対象は **p8 のコプロセッサアプリ `cpapp-b.bin`**（18,090,880 バイト、
SHA-256 `f5a47758…56a1428`）。
`0700_part_image/dev/nflasha8_unpacked/cpapp-b.bin`。

## テーブルの形

`0xdd81d8` から **38バイト × 53レコード**。各レコードは u16 × 19：

| 位置 | 内容 |
| --- | --- |
| u16 0〜7 | 水平グループ。`[3]` が**水平有効幅** |
| u16 8〜15 | 垂直グループ。`[4]`（全体の12番目）が**垂直有効高さ** |
| u16 16〜18 | 常に 0 |

`scripts/locate_sensor_table.py` が値から自動で見つけて全件デコードする。
出力は [evidence/sensor-table-a7cii-201.json](../evidence/sensor-table-a7cii-201.json)。

## 肝心の2レコード

| オフセット | サイズ | 垂直グループ |
| --- | --- | --- |
| `0xdd82e2` | **7008 x 4672** | `[34, 24, 8, 8, 4672, 8, 8, 0]` |
| `0xdd8308` | **7008 x 4672** | `[34, 24, 8, 8, 4672, 8, 8, 0]` |
| `0xdd832e` | 7008 x **3942** | `[34, 24, 2, 8, 3942, 8, 2, 0]` |
| `0xdd8354` | 7008 x **3942** | `[34, 24, 2, 8, 3942, 8, 2, 0]` |

- 7008 x 4672 = **センサー全面（3:2）**。ファームウェア自身が持っている。
- 7008 / 3942 = **1.7778 = 16:9**。これが今の 4K 撮影で読んでいる窓。
- 2つのレコードの違いは**3フィールドだけ**：垂直グループの `[2]`（2 ⇔ 8）、
  `[4]`（3942 ⇔ 4672）、`[6]`（2 ⇔ 8）。

A7 IV キットの step 2 が変えているのも、同じ形のレコードの
「window field 11」「stream-0 active height」「window field 15」の3つで、
**構造が一致している**（アドレスは当然違う）。

## 付随フィールド

同じ近傍に、A7 IV デザインが触っている残りの値もある：

| 値 | オフセット | 意味 |
| --- | --- | --- |
| 366 | `0xdd8b44`、`0xdd8b52`（他に `0xdd95b4`） | 垂直センタリングオフセット。**(4672 − 3942) / 2 = 365** なので、短い窓を中央に置くための値 |
| 403 | `0xdd8b48`、`0xdd8b56`（他 4件） | 366 と対になる LC フィールド |
| 2011 | `0xdd8d26`、`0xdd8d3a` | 読み出し長（ライン周期） |

## 候補デザイン（old バイトのみ検証済み）

| デザイン | 内容 |
| --- | --- |
| [og_window_fullheight_v0](../designs/og_window_fullheight_v0.json) | 3942 の2レコードの垂直グループを、4672 レコードと同じ3値にする（6パッチ） |
| [og_voffset_zero_v0](../designs/og_voffset_zero_v0.json) | センタリングオフセット 366 → 0 と、対の 403 → 19（4パッチ） |

どちらも `scripts/verify_design.py` で全 `old` が一致する：

```bash
python3 scripts/verify_design.py designs/og_window_fullheight_v0.json \
  --image "cpapp=<p8>/cpapp-b.bin"
```

**一致は「このファームウェアのそのアドレスに確かにその値がある」ことしか
意味しない。** 効くかどうか、他に何が連動するか、カメラが起動するかは
全部未検証。

## 読み出し長をまだ含めていない理由

2011 は 3942 行を読む時間。全高にすると比例で
2011 × 4672 / 3942 ≈ **2384** になるはずで、A7 IV キットが使っている値
（2382、`0x094e`）とほぼ一致する。だが「ほぼ」で当てる値ではないので、
周辺レコードの構造を読んで**根拠のある値を出してから**デザインに入れる。

## 出力サイズ表（特定済み・2026-11-24）

同じ `cpapp-b.bin` の **`0xbefe38`** に、4K 幅の出力サイズが4件並んでいる：

| オフセット | サイズ | 比 |
| --- | --- | --- |
| `0xbefe38` | 3840 x 2160 | 16:9（現行の 4K 出力） |
| `0xbefe3c` | 3840 x 2880 | 4:3 |
| **`0xbefe40`** | **3840 x 2560** | **3:2 ← オープンゲートが欲しい出力** |
| `0xbefe44` | 3840 x 3840 | 1:1 |

**つまり 3840x2560 は Sony 自身の表に既に入っている。** 作る必要はなく、
選ばせる話になる。

構造の裏づけ：直前にも同じ「幅ごとに4変種」の並びがある。

| 幅 | 16:9 | 4:3 | 3:2 | 1:1 |
| --- | --- | --- | --- | --- |
| 960 | 960x540 | 960x720 | 960x640 | 960x960 |
| 7952 系 | 7952x4472 | 7072x5304 | 7952x5304 | 5304x5304 |
| 3840 | 3840x2160 | 3840x2880 | **3840x2560** | 3840x3840 |

（7952 幅の組は 42MP 機のもので、A7C II の 33MP ではない。
`cpapp-b.bin` は機種共通の部分を持っている）

再現： `scripts/locate_output_sizes.py`。出力は
[evidence/output-sizes-a7cii-201.json](../evidence/output-sizes-a7cii-201.json)。

なお A7 IV の `og57n_v1` が触っている `0xbf7638`（kind `R`）は、
この表と同じ `0xbf6`〜`0xbf7` 帯にある。出力側の作業がこの近傍で行われている
という見立てと整合する。
