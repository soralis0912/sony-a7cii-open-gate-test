# デザイン JSON の形式

1つのデザイン＝「この電源が入っている間だけカメラに当てるバイトパッチの集合」。
A7 IV キットの形式に合わせてあるので、考え方はそのまま読み替えられる。

```json
{
  "design": "og4k_v1",
  "model": "ILCE-7CM2",
  "firmware": "2.01",
  "target": {
    "file": "p15 /usr/lib/appFw.so",
    "sha256": "2ea02f7e…"
  },
  "patches": [
    {
      "kind": "S",
      "addr": "0xd95c42",
      "old": "660f",
      "new": "4012",
      "where": "file",
      "note": "stream-0 active height 3942 -> 4672"
    }
  ]
}
```

| フィールド | 意味 |
| --- | --- |
| `design` | デザイン名。ファイル名と合わせる |
| `model` / `firmware` | 対象。別機種・別版数に当ててはいけない |
| `target.sha256` | 当てる先のイメージのハッシュ。これが違えばアドレスも違う |
| `patches[].kind` | 分類の札（A7 IV キットは `S`＝センサー系、`R`＝レジスタ系などを使う）。照合には影響しない |
| `patches[].addr` | `where` のイメージ内のオフセット（16進文字列） |
| `patches[].old` | そこに**あるはず**のバイト列（16進）。照合に使う |
| `patches[].new` | 書き込むバイト列。長さは `old` と同じでなければならない |
| `patches[].where` | どのイメージか。既定は `file`。複数ある場合は名前を分ける |
| `patches[].note` | その数値が何なのか、どう特定したのか |

## 規則

1. **`new` と `old` は同じ長さ。** 長さが変わるパッチは作らない。
2. **`old` は必ず照合する。** カメラに送る前に
   `scripts/verify_design.py` を通す。1つでも外れたらそのデザインは使わない。
3. **`note` を空にしない。** 数値の意味と特定根拠が書かれていないパッチは、
   半年後の自分には再検証できない。
4. **1デザイン＝1つの目的。** 「出力サイズ」と「背面液晶」を混ぜない。
   A7 IV キットがステップに分けているのと同じ理由で、切り分けられないと
   どれが効いたのか分からなくなる。
